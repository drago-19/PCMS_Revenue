# แผนแก้ประสิทธิภาพ PCMS_Revenue — ทั้งระบบ

ที่มา: รายงานตรวจวัด 12 พ.ย. 2026 (prod จริง + production build ในเครื่อง)
หลักการที่ยึดทั้งแผน: **ข้อมูลเท่าเดิมทุกตัวเลข — เปลี่ยนแค่รูปการโหลด**

- ห้ามแก้ยอด จำนวนแถว ลำดับ หรือเลขเอกสารเพื่อให้เร็วขึ้น (ผูกกับกฎข้อ 4 ใน `AGENTS.md`)
- ทุกข้อต้องวัดก่อน/หลังด้วยชุดคำสั่งเดียวกันในหัวข้อ "วิธีวัดซ้ำ"
- ข้อไหนทำให้ข้อมูลเก่าได้ (แคช) ต้องบอก TTL และจุด invalidate ให้ชัด

## ตัวเลขตั้งต้น (baseline)

| หน้า | TTFB prod | HTML | DOM node | ข้อมูลต่อคลิก | กด→ขึ้น (prod, CPU ปกติ) |
|---|---|---|---|---|---|
| `/bills` | 125 ms | 560 KB | 1,530 | 107 KB | 176–473 ms |
| `/accounting` | 188 ms | 403 KB | 1,588 | 99 KB | — |
| `/history` | 135 ms | 345 KB | 1,083 | — | — |

บน CPU ที่ช้ากว่าเครื่องวัด 4 เท่า: กด→ขึ้น 0.5–2.0 วิ (หนักสุด `/accounting` 1.6–2.0 วิ, `/bills` 1.0–1.8 วิ)

อื่น ๆ ที่วัดไว้: 46–57% ของ HTML คือ RSC payload ที่ฝังมาเพื่อ hydrate · prefetch ยิง 18–29 คำขอต่อการเปิดหน้า (ตอบเป็น payload บางส่วน ~1.2 KB ไม่ได้รัน query ของหน้า) · ทุกหน้าเป็น `force-dynamic` ไม่มีแคชที่ไหนเลย · CDN ตอบ `DYNAMIC`

## เงื่อนไข "ข้อมูลทุกอย่างต้องไม่หาย" (ตรวจทุกข้อก่อน merge)

1. ยอดสรุปทุกช่อง (รายได้ / ค่าส่ง / ค่าธรรมเนียม / ยอดชำระสุทธิ) ต้องเท่าเดิมทุกหลัก
2. จำนวนบิลต่อหมวดและต่อช่องทางต้องเท่าเดิม (เช่น TikTok 61,605 ใบ · Shopee 3,989 ใบ บนข้อมูล prod)
3. จำนวนแถวที่แสดงต่อหน้า 20 แถวเท่าเดิม และการแบ่งหน้าเดิม
4. ใบกำกับภาษี / ใบพิมพ์ / กระดาษแพ็ค ต้องออกมาเหมือนเดิมทุกบรรทัด (ตรวจจริง 3 ใบ: TikTok · Shopee · Facebook)
5. ป๊อปอัปดูบิลต้องแสดงข้อมูลครบเหมือนเดิม (ข้อ P1 เปลี่ยนแค่ "ตอนไหน" ที่โหลด ไม่ใช่ "อะไร")
6. `invoice_registry` และเลขที่ออกไปแล้วห้ามหาย (กฎเดิมใน `AGENTS.md` ข้อ 3)

## งานที่ต้องทำ เรียงตามผลตอบแทนต่อแรง

### P1. เลิกส่งแถวทั้งก้อนเข้า client component — `/bills` ก่อน (ผลมากสุด)

**สภาพตอนนี้:** `BillTableRow` รับ `row: TransactionRow` เต็มออบเจกต์ (`src/components/BillPreviewDialog.tsx:91`) ทำให้ทุกแถวถูก serialize ลง payload อีกชุดนอกจาก markup — 22 แถวในตารางสร้าง `<script>` 140 ก้อน, payload ฝังในหน้า 319 KB (57% ของหน้า)

**แก้:**
- ให้ `BillTableRow` / `BillPreviewTrigger` รับเฉพาะ `orderId` + ฟิลด์ที่แสดงจริงในแถว
- เปิดป๊อปอัปดูบิล → ยิง `GET /api/bills/[orderId]/preview` (ทำตาม pattern ของ `src/app/api/bills/[orderId]/channel/route.ts`) แล้วดึง `TransactionRow` เต็มจาก loader เดียวกันกับที่หน้าใช้
- ป๊อปอัปมีสถานะ loading/error ครบตามกฎข้อ 1

**ผลที่คาด (ประมาณจาก baseline):** payload ฝัง `/bills` 319 KB → ~80 KB, ข้อมูลต่อคลิก 107 KB → ~35 KB

**ผลที่วัดได้ (ทำแล้ว 12 พ.ย. 2026):** `/bills` HTML 560,193 → **494,400 B** · payload ฝังในหน้า 319,189 → **235,972 B** · RSC ต่อคลิก 169 KB → **72 KB** · กด→ขึ้น (CPU ×4) 1,471 → **1,075 ms** · ป๊อปอัปเปิดใน **240 ms** และ API (`/api/bills/[orderId]/preview`) คืนข้อมูลครบ (`invoiceNo`, `channel`, `omsItems` 6 รายการ, `sellerSettings`) ทั้งรหัสออเดอร์แบบธรรมดาและแบบผสม `A|B|C` · ที่ 390px หน้าและ Dialog ไม่ล้นจอ
**เสี่ยง:** ป๊อปอัปช้าลงเล็กน้อยตอนเปิดครั้งแรก (มี loading state ครอบ) · ต้องตรวจว่าข้อมูลในป๊อปอัปครบเท่าเดิม (ข้อ 5)

### P2. ทำแบบเดียวกับ P1 กับตารางอื่น — ตรวจแล้วได้ผลเฉพาะ `/bills`

**ผลตรวจ 12 พ.ย. 2026 (วัดจริงก่อน-หลัง):**
- `/history` — แถวส่งแต่ค่าสเกลาร์อยู่แล้ว (`importId`, `filename`, `fileType`, `rowCount`, `isAccounting`, `periodStart`) ไม่มีออบเจกต์เต็มให้ตัด → ไม่มีอะไรให้ทำ
- `/products` — แถวส่ง `ProductStockRow` 12 ฟิลด์ (~300 B/แถว) ซึ่งเป็นค่าที่ dialog ต้องใช้เติมช่องกรอกทันที; จุดที่เสียเปล่าจริงคือ prop `rows` ที่ส่งอาร์เรย์ 20 แถวเข้า `StockTableClient` แต่ **ไม่ถูกใช้เลย** → ลบออกแล้ว
  - วัด `?tab=stock`: html 375,883 → **375,324 B** · inline payload 185,683 → **185,124 B** = **−559 B (0.3%)** — เพราะ flight payload อ้างอิงออบเจกต์ที่ซ้ำอยู่แล้ว จึงเกือบไม่มีผล
- **สรุป: P2 ปิดที่สองหน้านี้** — น้ำหนักที่เหลือเป็นการเรนเดอร์ markup ไม่ใช่ props; ถ้าจะลดอีกต้องเปลี่ยนโครงแถว (เหมือน P6) หรือย้ายไปทำงานที่ `/orders` (HTML 1.19 MB) ซึ่งคุ้มกว่า

รายละเอียดเดิมของข้อนี้:

- `/products`: แถวส่ง `StockEditDialog` ต้องโหลดรายละเอียดตอนเปิด (`src/app/products/page.tsx:394,477,556,617`)
- `/history`: ลิงก์และแถวที่ส่งข้อมูล import เต็มก้อน (`src/app/history/page.tsx:358`)
- `/orders`: การ์ดออเดอร์ 83 ใบ + 138 ชิ้นในหน้าเดียว → แบ่งเป็นหน้า/แท็บตามรอบ (ข้อมูลเดิม แค่ไม่ต้องเรนเดอร์ทั้งหมดพร้อมกัน) เป้า DOM ≤ 800 node
- `/accounting`: แท็บรายงานที่ไม่ได้เปิดอยู่ไม่ต้องเรนเดอร์ (แยก route หรือ lazy)

**ผลที่คาด:** `/orders` 1.19 MB → เป้า ≤ 250 KB ต่อการเปิดหน้า · `/products`, `/history` ลด payload 40–60%

### P3. `loading.tsx` ให้ครบทุก route

**สภาพตอนนี้:** มีแค่ `src/app/orders/loading.tsx` — และ `/orders` คือหน้าที่ให้ความรู้สึกเร็วที่สุด (0.27 วิ ที่ CPU ×4) แม้ข้อมูลจะหนักที่สุด

**แก้:** เพิ่ม `loading.tsx` ทุก route โดยใช้ `TableLoadingBoundary` / `TableSkeleton` ที่มีอยู่แล้ว และให้ความสูง skeleton ตรงกับตาราง (`recordTableRegionHeight` มีอยู่แล้วใน `src/components/TableSkeleton.tsx`) — ทำให้ prefetch แบบ partial มีความหมายและผู้ใช้เห็นอะไรทันทีที่กด

**ผลที่คาด:** เวลากด→เห็น reacted ครั้งแรก < 100 ms ทุกหน้า (คุณภาพการรับรู้ ไม่ใช่เวลาข้อมูลมาถึง)

### P4. ปิด prefetch ที่ลิงก์ตัวกรอง/ลิงก์ในแถว

**สภาพตอนนี้:** เปิด `/bills` ครั้งเดียวยิง 18–29 คำขอ RSC ที่ตอบกลับ ~1.2 KB และเอาไปใช้ต่อไม่ได้

**แก้:** ใส่ `prefetch={false}` ให้ลิงก์ที่มี query param (ตัวกรอง/แถว) — Sidebar ทำถูกอยู่แล้ว (`src/components/Sidebar.tsx:369,392,438,502,560,616,680`)
ไฟล์ที่ต้องแก้: `src/components/BillsFilterInteractive.tsx:273,294,313,361,489,980` · `src/components/BillsShopTabs.tsx:105,131` · `src/components/BillsShippingHeaderFilter.tsx:130,151,172,193,214,241,259` · `src/app/products/page.tsx:394,477,556,617` · `src/app/history/page.tsx:358`
เมนูหลัก 5 หน้า: ให้ prefetch ตอน `onMouseEnter`/`onFocus` ด้วย `router.prefetch` (แบบที่ `src/components/BatchPicker.tsx:47` ทำอยู่) แทน prefetch ทั้ง viewport

**ผลที่วัดได้ (ทำแล้ว):** /bills 28 → 6 · /products 27 → 5 · /history 20 → 4 คำขอ (ที่เหลือคือลิงก์เมนู `/` และ `/import` ที่ไม่มี query param) · ยอดและจำนวนแถวเท่าเดิม ("รวมทั้งหมด (37,958 รายการ)", 22 แถว)

### P5. ให้ router cache ใช้ได้จริง (ต้องให้เจ้าของระบบตัดสิน)

**สภาพตอนนี้:** กด back กลับหน้าที่เคยเปิด ยังยิงคำขอใหม่ (230 ms) เพราะทุกหน้า `force-dynamic`

**แก้ (เลือกอย่างใดอย่างหนึ่ง):**
- **5a (ปลอดภัยสุด):** ไม่เปิดแคช — พึ่ง P1–P4 อย่างเดียว ข้อมูลสดเสมอ
- **5b:** เปิด `experimental.staleTimes = { dynamic: 30, static: 180 }` ใน `next.config.ts` (คีย์มีจริงใน Next 16: `node_modules/next/dist/server/config-shared.d.ts:459`) → กลับหน้าเดิม/ไปหน้าที่เพิ่งเปิด เร็วขึ้นทันที แต่ข้อมูลอาจเก่าได้ไม่เกิน 30 วิ; ต้องเรียก `router.refresh()` หลังบันทึกทุกครั้ง (ตรวจ dialogs ที่มีการเขียนข้อมูล)
- **5c:** แคชระดับข้อมูลด้วย `unstable_cache` ต่อ loader โดยใช้ version key ที่ bump ตอน import (ต่อยอดจาก `clearDailyBatchesCache()` / `clearUploadCompletenessCache()` ใน `src/lib/queries.ts:1674,5216`) — ข้อมูลสดเพราะ invalidate ตอนเขียน

**คำแนะนำ:** เริ่มที่ 5a + P1–P4 ก่อน แล้วค่อยพิจารณา 5b/5c ด้วยตัวเลขหลัง P1

### P6. ลด DOM ต่อแถว — ตรวจแล้ว “ไม่มี cell ที่เรนเดอร์ซ้ำ”

**วัดจริง (12 พ.ย. 2026):** `/bills` มี 7 `TableCell` ต่อแถว · 44 element ต่อแถว · 7.8–8.5 KB ต่อแถว · 22 แถว = 1,602 DOM node ทั้งหน้า — **ไม่พบ cell ที่เรนเดอร์ซ้ำเพื่อ responsive** (ใช้ `Table variant="stack"` + `data-label` แทน)

class string ที่ซ้ำมากที่สุดมี 3–4 แบบ รวมกัน ~20 KB (~4% ของ HTML) — รวมเป็น `cva` ได้แต่ผลตอบแทนน้อย · ถ้าจะลดอีกต้องเปลี่ยนโครงแถว (ลดคอลัมน์/รวมช่อง) ซึ่ง **เปลี่ยนหน้าตา** ขัดเงื่อนไขข้อมูลเท่าเดิม → ต้องให้เจ้าของระบบตัดสินก่อน

รายละเอียดเดิมของข้อนี้:

- `/bills`: แต่ละ cell ถูกเรนเดอร์ซ้ำเพื่อ responsive (`min-[768px]:max-[899px]:hidden` ใน `src/app/bills/page.tsx`) → เลือกโครงเดียวต่อช่วงความกว้าง หรือย้ายไป variant `cva`
- เป้า: `/bills`, `/accounting`, `/history` ≤ 800 node ต่อหน้า (ตอนนี้ 1,083–1,588)
- เหตุผลตัวเลข: 38–44% ของเวลาโปรไฟล์คือการสร้าง/จัดวาง DOM และ 24–33% คือ forced layout ของ subtree ทั้งก้อน (scroll-restore ของ Next)

### P7. งานฝั่งข้อมูลสองจุด (ไม่เร่ง แต่ควรทำ)

- `/import`: รอบแรกหลังแคชหมดอายุ 515–536 ms — ฟังก์ชันความครบถ้วนเรียก 6 query (`src/lib/queries.ts:5243–5442`) ตัวหนักคือ aggregate ที่มี `EXISTS` ต่อแถวบน `oms_order_items` (`src/lib/queries.ts:5288`) → ทำเป็น read model: สรุปความครบถ้วนรายวันเขียนลงตารางตอน import แทนการคำนวณใหม่ทุกครั้ง (ข้อมูลยังมาจากไฟล์เดียวกัน)
- `/accounting`: 15–29 ธุรกรรมต่อ render → รวมเป็น query เดียวหรือ `Promise.all` ให้ชัด (ตรวจด้วยเทคนิคในหัวข้อ "วิธีวัดซ้ำ")
- ทุกจุดที่เพิ่มแคช: ต้อง invalidate ใน `import-service` เหมือนที่ทำอยู่แล้ว

### P8. ด่านกันไม่ให้กลับมา (บังคับใช้จริง)

สคริปต์ `scripts/perf-budget.ts` วัด 6 หน้า (`/`, `/bills`, `/products`, `/accounting`, `/history`, `/orders`) บน build production ในเครื่อง แล้ว fail เมื่อเกินงบ:

| ตัวชี้วัด | งบ |
|---|---|
| HTML ต่อหน้า | ≤ 200 KB |
| RSC payload ที่ฝังในหน้า | ≤ 80 KB |
| DOM node ต่อหน้า | ≤ 800 |
| คำขอ prefetch ต่อการเปิดหน้า | ≤ 6 (ลิงก์ที่มี query param ต้องไม่ prefetch เลย) |
| ธุรกรรม DB ต่อการเรนเดอร์ | ≤ 10 |

ต่อเข้า `pnpm test:perf` และใส่ในขั้นตอนก่อนส่งงาน (กฎข้อ 6 ใน `AGENTS.md`)

## ลำดับที่แนะนำ

1. **P4 + P3** (ถูกที่สุด ได้ผลทันที: ตัดคำขอ 18–29 ต่อหน้า และมี skeleton ทุกหน้า)
2. **P1** (คอขวดจริง: payload ต่อการกด) แล้ววัดซ้ำ
3. **P2 + P6** ไล่ทีละหน้า เริ่มที่ `/orders` (1.19 MB) และ `/accounting` (1.6–2.0 วิ)
4. **P8** ตั้งด่านก่อน เพื่อไม่ให้งานที่แก้แล้วถอยหลัง
5. **P5 / P7** ตัดสินด้วยตัวเลขหลังข้อ 1–3

## วิธีวัดซ้ำ (ชุดเดียวกับรายงาน)

- build + start: `pnpm build` แล้ว `pnpm exec next start -p 3012` (พอร์ต 3002 ถูก wslrelay ถืออยู่บนเครื่อง dev)
- TTFB/ขนาด/ธุรกรรม DB: `curl` ต่อหน้า 3 รอบ + นับ `pg_stat_database.xact_commit` ก่อน/หลัง (แยกช่วง 2.5 วิ, คลาดเคลื่อน ±2)
- กด→ขึ้น/CPU: puppeteer-core + `Emulation.setCPUThrottlingRate {rate: 4}` แล้วจับ `performance.now()` จากคลิกถึง `h1` เปลี่ยน
- prefetch: `Network.requestWillBeSent` กรอง `_rsc=`
- prod: เปิด `https://revenue.goldpulse-ai.com` ในเบราว์เซอร์ที่ล็อกอิน แล้วอ่าน `performance.getEntriesByType('navigation')`
